Sparewall is an open-source, image-based Linux firewall. Describe the whole deployment in one versioned document; every change is validated, applied atomically, and rolled back unless you confirm it.

site.yaml

schema: 1
cluster: { nodes: [fw1] }
management: { network: mgmt }
ports:
  fw1:
    uplink: { nic: "52:54:00:aa:00:01" }
networks:
  mgmt:  { port: uplink, role: management,
           addresses: { fw1: 10.0.99.2/24 } }
  wan:   { port: uplink, vlan: 10, role: wan,
           dhcp_client: true }
  users: { port: uplink, vlan: 20,
           addresses: { fw1: 192.0.2.2/24 },
           vip: 192.0.2.1/24 }
zones:
  wan:   { networks: [wan] }
  users: { networks: [users] }
policy:
  users->wan: { action: accept, nat: masquerade }
  wan->self:  { action: drop }
dhcp:
  users: { pool: 192.0.2.100-192.0.2.199 }

A firewall you can reason about

Sparewall treats a firewall like any other piece of infrastructure: declared, versioned, reviewable, and safe to change.

Image-based and rollback-safe

The OS is a signed bootc image. An upgrade is a reboot into the new image; a rollback is a reboot into the old one.

One source of truth

One JSON or YAML document describes ports, networks, zones, policy, NAT and services. Every change becomes a numbered generation you can diff, list and roll back to.

Changes that undo themselves

Apply with a confirm timer. If the change cuts you off, the node reverts on its own. Anti-lockout keeps the management path open.

HA when wanted, not required

The same image and document shape run one node or an active/standby pair, with VRRP, connection-state sync and DHCP failover over a WireGuard tunnel.

Zones plus raw rules

Write policy between zones for the common case, and drop to raw nftables rules when you need to. Sparewall owns its own table and never flushes anyone else's.

Swappable services

DHCP, DNS and time run as containerized providers behind a stable interface: Kea, Unbound and chrony by default.

How a change happens

The sparewall CLI is a thin client for sparewalld, the coordinator on each node. The coordinator is the only thing that writes daemon configuration.

  1. ValidateThe schema first, then semantic checks: overlapping subnets, rules naming missing zones, pools outside their subnet.
  2. Render and dry-runPure renderers produce networkd, nftables, keepalived and provider configuration, and each file is checked by its own tool.
  3. ActivateThe new generation goes live as a unit, reloading only what changed, and the confirm timer starts.
  4. Confirm or revertConfirm to keep it. Miss the deadline and the previous generation comes back, so a change that cuts off your access undoes itself.
  5. Sync the peerIn a pair, the confirmed generation is pushed through the sync tunnel and goes through the same steps on the other node.

shell

$ sparewall apply -f site.yaml --confirm 120
# reverts in 120s unless confirmed
$ sparewall confirm
$ sparewall set networks.users.vip=192.0.2.254/24
$ sparewall get policy.'users->wan' -o yaml
$ sparewall history

Built from standard parts

Almost everything in Sparewall is software you already know. The new code is the coordinator and its CLI, written in Rust.

Roadmap

Sparewall is built bottom-up, and each milestone ends with tests that run in CI. It is not yet ready for production use. The full plan is in the design document.

  1. 0
    FoundationsCI, a signed bootc image, license gates
  2. 1
    Standalone coreCoordinator, CLI, schema v1, confirm and rollback
  3. 2
    ServicesDHCP, DNS, time, metrics, backup and restore
  4. 3
    High availabilityActive/standby pairs, flow and lease continuity
  5. 4
    Access and secretsUsers and roles, ACME, remote-access WireGuard
  6. 5
    Releases and upgradesChannels, health-gated upgrades, installers
  7. 6
    Production0.x releases at real sites: hardening, benchmarks, documentation
  8. 7
    Web UI and HTTP APIOpt-in, with roles for every user; then 1.0
