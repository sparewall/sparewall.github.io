Open-source Linux firewall

One document.

Sparewall is an open-source, image-based Linux firewall. Describe the whole deployment in one versioned document; every change is validated, applied atomically, and rolled back unless you confirm it. Drive it from the CLI, the HTTP API or a web UI.

A firewall you can reason about

Sparewall treats a firewall like any other piece of infrastructure: declared, versioned, reviewable, and safe to change.

Upgrades without surprises

  • Rolling, health-gated upgrades: in a pair, the backup goes first, and the master follows only once it is healthy.
  • Start one from the CLI or the web UI, or let the node upgrade itself in a maintenance window. It accepts only signed images.
  • A background check shows new releases in sparewall status, the login banner and the web UI.

Pairs you control

  • sparewall failover moves the gateway back when you choose, from either node.
  • Upgrades and configuration changes start from either node, and the pair stays in step.
  • A two-NIC pair needs no VLANs. Running a pair covers the layouts and what each isolates.

Users, roles and secrets

  • Named users and API tokens, each with a role: monitor, viewer, operator or admin.
  • Secrets are encrypted on the node, bound to its TPM where it has one, and shared with the peer.
  • management.sources limits which hosts reach SSH and HTTPS.
  • The coordinator runs in its own enforcing SELinux domain, and the web UI's gateway is an unprivileged, sandboxed service.

Networking in detail

  • Raw nftables rules beside zone policy, for what zones don't cover. Sparewall never flushes anyone else's tables.
  • IPv6 by DHCPv6 with prefix delegation, SLAAC or static, with router advertisements inside and no renumbering at a failover.
  • Rules can name a host by its suffix in a delegated prefix, and keep matching when the ISP renumbers it.

Day-to-day operations

  • Troubleshoot without SSH: logs, logged traffic, neighbours and routes, ping, traceroute, DNS lookups and short packet captures, from the CLI or the web UI, and from either node of a pair.
  • Backups run on a schedule and prune themselves to a retention policy; check the password from your workstation before you need it.
  • Logs forwarded to any syslog collector, over UDP, TCP, TLS or RELP.
  • The CLI for Linux and macOS, x86_64 or arm64, from Homebrew, with shell completions and -o json for scripts.

Planned

  • Pi-hole as a containerized DNS provider.
  • PXE options for network boot.
  • DHCPv6 on inside networks, and IPv6 through VPN tunnels, after 1.0.

A web UI, when you want one

A node can serve a web UI and an HTTP API on its management network. Both stay off until the document turns them on with sparewall set management.web=true. SSH, the console and the CLI never depend on them.

  • Each page offers only what the user's role allows, and the node checks every call regardless.
  • The status page charts throughput, CPU, memory, connection-tracking table use and rule hits over the last hour, day or week, when the node keeps its metrics history.
  • The Logs, Logged traffic and Network pages cover troubleshooting, down to a packet capture downloaded as a pcap. In a pair, each has a switch to the other node's view.
  • Admins see when an update is available and can start the upgrade there, and manage users and tokens. A new password is hashed in the browser, so only the hash reaches the node.
  • The UI loads nothing from outside the node.
  • Scripts use the same API with a token: POST /call/<interface>.<Method>, described by an OpenAPI 3.1 document at /openapi.json. The UI's API page lists every call with the role it needs and a curl example.

How a change happens

The sparewall CLI is a thin client for sparewalld, the coordinator on each node. The coordinator is the only thing that writes daemon configuration.

  1. ValidateThe schema first, then semantic checks: overlapping subnets, rules naming missing zones, pools outside their subnet.
  2. Render and dry-runPure renderers produce networkd, nftables, keepalived and provider configuration, and each file is checked by its own tool.
  3. ActivateThe new generation goes live as a unit, reloading only what changed, and the confirm timer starts.
  4. Confirm or revertConfirm to keep it. Miss the deadline and the previous generation comes back, so a change that cuts off your access undoes itself.
  5. Sync the peerIn a pair, the confirmed generation is pushed through the sync tunnel and goes through the same steps on the other node.

site.yaml

schema: 1
cluster: { nodes: [fw1] }
management: { network: lan, sources: [192.168.1.10] }
ports:
  fw1:
    wan0: { nic: "52:54:00:aa:00:01" }
    lan0: { nic: "52:54:00:aa:00:02" }
networks:
  wan: { port: wan0, role: wan, dhcp_client: true,
         ipv6: { mode: dhcpv6 } }
  lan: { port: lan0, role: management,
         addresses: { fw1: 192.168.1.1/24 },
         ipv6: { mode: delegated, subnet_id: 1 } }
zones:
  wan: { networks: [wan] }
  lan: { networks: [lan] }
policy:
  lan->wan:  { action: accept, nat: masquerade }
  wan->self: { action: drop }
dhcp:
  lan: { pool: 192.168.1.100-192.168.1.199 }
dns: { enabled: true }

shell

$ sparewall apply -f site.yaml --confirm 120
# reverts in 120s unless confirmed
$ sparewall confirm
$ sparewall set dhcp.lan.pool=192.168.1.50-192.168.1.199
$ sparewall get policy.'lan->wan' -o yaml
$ sparewall history

Who it's for

Homelabs and small offices: one node, or an active/standby pair when the network has to stay up through a failure or an upgrade.

What it runs on

  • A mini PC or any other x86_64 machine, with any NIC the Fedora kernel supports.
  • A VM on QEMU/KVM with virtio NICs. The image carries the QEMU guest agent; give a libvirt VM a virtual TPM.
  • A TPM is optional and recommended: secrets are sealed to it where there is one.

Port layouts

  • Two ports, WAN and LAN, behind a plain switch with no VLANs: the usual setup.
  • One port carrying every network as a tagged VLAN.
  • LACP or active-backup bonds. A pair also needs a link between its nodes for sync: a network of its own, or the LAN.

Install

Every release carries an installer, disk images and the CLI, with SBOMs and signed checksums. The image is also at ghcr.io/sparewall/sparewall, and nodes on the stable channel are offered each new release, or upgrade themselves in a maintenance window.

1. The CLI

On Linux or macOS, x86_64 or arm64:

$ brew install sparewall/tap/sparewall

2. A node

Boot the ISO to install unattended to a blank disk, write the raw image to a disk, or use the qcow2 image for a virtual machine. All three are on the latest release.

3. Verify

Check the downloads against the project key, cosign.pub:

cosign verify-blob --key cosign.pub \
  --bundle SHA256SUMS.sigstore.json SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS

Getting started takes a node from a fresh install to a working firewall.
